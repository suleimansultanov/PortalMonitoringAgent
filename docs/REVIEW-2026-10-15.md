## 1. Критично — деньги и целостность данных

### 1.1 Склейка (`resolve`) переписывает ~18 000 строк каждую ночь — это и есть «15–48 минут»
`matching/resolve.ts:296-318` (`sameValue`). Для `matchSignals` сравнение идёт
через `JSON.stringify`; Postgres возвращает jsonb с ключами в своём порядке,
объект из `score.ts` — в порядке вставки. Строки никогда не равны → каждая
запись каждой склеенной группы обновляется ночью. Замер по базе 14.10 01:00:
**18 066 активных объявлений получили `updated_at` без скачивания, 17 974 из них
в склеенных группах**; при 100–250 мс на запрос это 30–75 минут.
**Фикс:** канонизировать ключи перед сравнением (одна строка) + тест.

### 1.2 Недельное обновление объявлений фактически не работает
`runner/run.ts:743, 830`. Очередь «перечитать раз в 7 дней» ключуется на
`updated_at`, а его двигают склейка (1.1), reparse, sanity. По базе: из
**15 868** активных объявлений, не скачанных >7 дней, **13 831 (87%) не видны
очереди**. Для порталов без даты в индексе это единственный механизм заметить
изменение цены. `refreshOnChange` для Stream.Estate это обошёл, остальные
источники — нет.
**Фикс:** ключевать на `last_seen_at` (пишет только ingest); индекс
`(source_id, status, last_seen_at)`.

### 1.3 Платный счётчик Stream.Estate V1 — три дыры (`streamV1.ts`, `streamestatev1.ts`)
1. **Нечисловой потолок отключает бюджет.** `Number("14,000")` = NaN; обе
   проверки `>` с NaN ложны → все страницы уходят. Фикс: `Number.isSafeInteger`,
   `anchorDay` 1–28, `max-pages` тоже.
2. **Журнал пишется после ответа.** Падение между ответом и записью теряет
   страницу из счёта; на Маке кэш пишется раньше журнала → страница навсегда
   «бесплатная». Два процесса (раннер и CLI) читают `totals()` одновременно и
   оба отправляют. Фикс: резервирующая запись `uncertain` до запроса и
   корректирующая после (журнал остаётся append-only).
3. **Водяной знак «с какого момента изменения» общий на источник** и
   двигается по `completed_at` прошлого прохода. Остановка по потолку
   посреди склада → остаток склада не берётся никогда; остановка посреди
   изменений → окно у непройденных коммун теряется (в т.ч. снятия, навсегда);
   не-бюджетная ошибка после 4 коммун → весь склад оплачивается второй раз.
   Фикс: состояние на (источник, коммуна): `stockedAt`, курсор склада,
   `changesSince`; двигать только по завершении обхода коммуны.
4. Мелкое: `stamp()` пишет UTC, API читает Europe/Paris → перекрытие 2–3 ч
   вместо 1 ч (≈25 items/ночь, ≈750/мес — почти весь резерв); граница
   периода — полночь UTC, а не момент подписки; `hydra:totalItems` не
   обязателен в схеме → при его отсутствии обход молча кончается на 1-й
   странице; обходы `created` и `re-priced` пересекаются (объект платится
   дважды — учитывать в сверке).

### 1.4 Тенантности нет ни в дашборде, ни во внутреннем API
`session.user.clientId` нигде не читается. `listMatches` отдаёт покупателей и
матчи всех клиентов; `PATCH /api/matches` меняет любой матч по id; отчёты
открываются по uuid без проверки владельца; `listReports` хардкодит
`med-estates`. Пока клиент один — латентно; первый пользователь второго
клиента увидит покупателей Med-Estates. `requireSession()` есть и не
используется.

### 1.5 `client_sources` не применяется в `/api/v1/properties` и `/events`
Ключ видит все включённые источники, а не те, на которые подписан клиент.
Документация (`API.md`, `keys.ts`) обещает иное. Фикс: `scope.sourceIds` в
предикат `SERVED_PROPERTY` и в `withListings`.

### 1.6 Ложные делистинги: 7 адаптеров пропускают ненастроенную коммуну без `ctx.incomplete`
`greenacres.ts:87`, `figaro.ts:143`, `jamesedition.ts:316`, `luxuryestate.ts:58`,
`smc.ts:386`, `superimmo.ts:71`, `etreproprio.ts:53`. Убери slug коммуны из
конфига «починить потом» — её склад этого источника снимется ночью, guard
не сработает (одна коммуна из двенадцати). Vizzit, Bien'ici, Zoopla, Figaro
Immobilier делают правильно. Фикс: один общий helper.

### 1.7 `sync-to-supabase.sh` — TRUNCATE продакшена без подтверждения
С 29.08 база одна; скрипт считает `.env.local` источником, а это и есть
Supabase. TRUNCATE 11 таблиц, дамп — временный файл, удаляемый при выходе.
`DEPLOY.md` до сих пор велит его запускать. Фикс: удалить скрипт (его задача
закончилась 29.08) или отказ при совпадении хостов + `--yes`.

### 1.8 `dump-data.sh` не бэкапит `client_api_keys` и `api_usage`
Восстановление из дампа теряет ключи клиента и обнуляет счётчик V1 (потолок
перестаёт защищать). Фикс: добавить таблицы + тест, сверяющий список со схемой.

## 2. Важно — правильность данных и событий

- **Фантомные `price_changed`/`updated`** (`ingest.ts:157-215`): события
  считаются от несанированного парса, строка — от санированного.
  «De 5 000 000 à 10 000 000» → строка верна, в журнале `priceTo = 5e14`.
  Фикс: строить `after` из `incoming`.
- **Побайтово тот же HTML воскрешает снятое объявление** без `relisted` и
  с оставшимся `delisted_at` (`ingest.ts:73-81`). Фикс: ярлык только при
  `existing.status === "active"`.
- **Эвикция в склейке** (`resolve.ts:209-217`): если выброшенный аутлайер —
  корень union-find, `groups.set(row.id)` затирает оставленных; они не
  записываются, а аутлайер получает тот же старый `property_id` — раскол
  отменяется. Фикс: ключ `evicted:<id>`.
- **Нет retry к базе в раннере** (`withDbRetry` только в reparse). Один
  обрыв пулера на N-м объявлении → проход `error`, остаток брошен, **и
  делистинги не пишутся** при правильном discovery. 12 таких строк в
  `portal_runs`. Фикс: обернуть DB-работу ingest и `delistListings`.
- **changes-only источник каждую ночь помечает 12/12 коммун incomplete**
  (`streamestatev1.ts:305`) → ночь с одними снятиями грейдится FAIL
  («blocked door»). Раннер и так ставит `complete=false` для `changesOnly`;
  вызов в адаптере лишний.
- **Reparse двигает `occurred_at` событий в прошлое** (время снимка) →
  курсор `/events` их перешагивает навсегда. Фикс: `created_at` у событий,
  курсор по нему.
- **`sourceCount`** считает источники, не порталы: агрегатор = 1, выключенный
  источник считается. API обещает «сколько порталов». Фикс: считать по
  `listings[]` после разбиения.
- **Дашборд не применяет фильтр «только включённые источники»**, API —
  применяет: разные цифры «активных объектов», карточки с сентябрьскими
  ценами Figaro, фильтр по порталу предлагает выключенные. Плюс
  `properties.price_eur` склейка берёт из всей группы, включая мёртвые строки.
- **V2 пишет `createdAt` Stream.Estate в `publishedAt`** как fallback; V1
  этого не делает (это их дата обнаружения). **LuxuryEstate** пишет
  `datePosted`, который по собственному комментарию может быть датой
  регенерации страницы — и перезаписывается при каждом парсе.
- **`num()` в `jsonld.ts`** ломает английские тысячи: `"9,500,000"` → null,
  `"2,666"` → 2.666. Латентно (цены сейчас без запятых). Тестов на `jsonld.ts` нет.
- **Два параллельных прохода** одного источника пишут дубли событий
  (`listed`, `delisted`) — check-then-write. Фикс: `RETURNING` + событие
  только по возвращённым строкам.
- Figaro: fallback на цену в валюте посетителя (`figaro.ts:841`);
  Figaro Immobilier: `/NC|demande|consulter/` без границ слова — «financement»
  = «цена по запросу». Оба источника выключены, но код живой.

## 3. Производительность

- **Склейка:** 1.1 — главное. Далее: `candidatePairs` строит 11,9 млн пар
  для Sainte-Maxime (97,5% отсекаются по цене одной проверкой после
  аллокации), `shingles()` считается 6 раз на пару. Фикс: мемоизация
  shingles, блокировка по цене/мандату, генератор вместо массива.
- **Ingest:** 6–8 последовательных запросов к базе на объявление; для
  Stream.Estate и Bien'ici (записи на руках) это теперь узкое место, а не
  crawl delay (~1,5–2 с на объявление с US-раннера). Фикс: предзагрузка
  снимков/строк чанком по 25, мемоизация `resolveAgency`, батч событий.
- **`/status`** разворачивает jsonb всех активных записей обоих
  Stream.Estate при каждом вызове (не индексируется, растёт). Фикс:
  колонка `carried_portals text[]` при ingest + GIN.
- `withListings` тянет весь `raw` на 500 объектов ради 7 полей;
  `lastPriceChange` грузит все события без лимита; EXISTS по
  `priceOnRequest` скопирован трижды. Фикс: проекции jsonb, `DISTINCT ON`,
  колонка `price_on_request`.
- `refreshOnChange`: `distinct on` по всем снимкам источника (7 695 строк,
  растёт) под `query_timeout` 10 с. Фикс: ограничить id сегодняшней ночи.
- Листинг дашборда: OFFSET по неуникальному `first_listed_at` → повторы и
  пропуски между страницами; индекса нет. Фикс: tiebreaker по `id` + индекс.
- Нет индексов: `portal_listings (source_id) where status='active'`,
  `properties (commune_insee, id) where status='active'`.

## 4. Безопасность

- `PUBLIC_PREFIXES` мёртв (нигде не импортируется) и расходится с матчером
  middleware; хвост матчера `.*\.(svg|png|…)$` глобальный → `/portal/x.png`
  без сессии (сейчас 500 на uuid, но любая будущая страница без uuid открыта).
- Нет rate limit на логин и `/api/v1` (один ключ может тянуть `limit=500`
  с полным `raw` без потолка).
- Workflow inputs подставляются в `run:` напрямую (`collect.yml:159`,
  `superimmo.yml:118`, `probe.yml:60`) в шаге с секретами. Низкий риск
  (dispatch только с write-доступом), фикс три строки через `env:`.
- Нет `CHECK` на все статусные колонки (`status`, `type`, `role`, `kind`) —
  опечатка создаёт состояние, которое все фильтры молча игнорируют.
- Ошибки по uuid: `/api/v1/reports/{id}` с не-uuid → 500 вместо 404.

## 6. Что хорошо — и что беречь
